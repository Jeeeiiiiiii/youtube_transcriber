Prateek: Yeah, so a StatefulSet is something where — let's say I have many pods
          for a service — in StatefulSets it makes sure there's a dependency
          between the pods. Even the provisioning of the pods is sequential. It
          won't be like all pods coming up together and then shutting down

          updates, to make the scaling efficient. But in the case of a

          pod, and it doesn't require unique persistent storage per pod. But in
          a StatefulSet, each pod can be associated with a unique persistent
          volume. This ensures the pod's data is preserved across restarts or
          rescheduling, which makes it ideal for stateful applications where
          data persistence is crucial.

Aditya: Sure, Prateek. So how do you create a multi-stage Docker build?

Prateek: Yeah, so a multi-stage Docker build allows us to use multiple FROM
          statements in a single Dockerfile. Each has a separate build stage,
          and this becomes very useful when we have to create smaller and more
          efficient images by allowing us to copy only the necessary artifacts
          from one stage and remove everything else that's not required. So the
          major aspects of this technique: each FROM statement starts a new
          build stage, and we can have as many stages as we want. Each stage can
          use a different base image, and for artifact copying we can just copy
          the artifact from one stage to another using the COPY statement — we
          write 'COPY --from' with whatever stage we want to copy from. This
          approach is especially useful to have a complex build process where
          the build environment is different from the runtime environment. So
          let me give an example of a multi-stage build where we're building a
          Golang application. We can write 'FROM golang', some version, then set
          up the working directory, then copy the module manifests — go.mod and
          go.sum — and download the Go modules. Now we want to build the
          application, so we run a 'go build' command that builds the
          application. Now we create a minimal runtime image — we use a FROM
          statement with an Alpine image, set the working directory with the
          WORKDIR command, then copy the previously created build from the
          previous stage into this stage, and then we run the commands. So what
          are the benefits? Multi-stage builds help us create optimized Docker
          images by separating the build environment from the runtime
          environment, and they minimize the final image size. This becomes
          useful for production environments where smaller image sizes are
          preferred for faster deployment and a reduced attack surface.

Prateek: So there are several deployment strategies. The very famous one is

          ready to be served side by side. We try and test that particular set —
          so if we have V1 and we want V2 to be deployed, we make the entire

          the entire user base. How does it help? It minimizes downtime to
