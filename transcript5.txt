          upgraded. And there were two major problems. So our version of
          Kubernetes was very outdated. So the latest stable version we wanted
          Kubernetes to get upgraded to was almost three versions ahead, and in
          Kubernetes you cannot jump the version — you have to go step by step.
          But very few people will know that the control plane has to go step by
          step, while your node groups can jump a version upgrade, giving you a
          lot of time savings while you do that upgrade if you have this sort of
          a downgraded version currently. So because it's three levels down —
          another fact is that Kubernetes only supports two levels down for the
          node group. So for example, if my current version of the Kubernetes
          control plane is five, then that version can support a node group of
          version five, version four, and version three, but it will not support
          a node group of version two, and it will not support a node group of
          version six. So we upgraded our control plane one cluster at a time,

          we went straight to the final version we wanted, we could take the
          cluster there, but then our node groups would be obsolete and not
          supported by that control plane, which would result in a disaster for
          us. So we had to stop there. But when we were upgrading the node
          groups, we could easily jump a version — version three of a node group
          can be replaced with version five rather than going to four and then
          to five. And the way we did it is basically we added an extra set of
          nodes to the same cluster once the control plane got updated. Then
          that extra set of nodes was with version five, for example. Then we
          tainted all the old nodes, and because we were using autoscaling and
          each application had multiple nodes, one pod gets replaced at a time.

          applications even before all the pods from the previous nodes got
          deleted. So that way, my traffic was divided between these two, and at
          any given time the application was up and running either in the older
          node group or in the new node group. So that way we had almost no
          downtime for the entire application. And once we had moved everything

          letting Kubernetes schedule any new pods on those particular nodes —
          one node at a time, we moved everything, every pod, all the Kubernetes
          resources, to the new node group. And we repeated the same process for
          going from version four to five. That way, we moved up three versions
          of our cluster, of all of our node groups, and everything, and we had
          no downtime while doing the activity. This whole process we then
          automated — because we're DevOps engineers and we like to automate
          stuff — and for the rest of the clusters it happened with a few
          clicks, obviously a few manual clicks, and most of the things were
          managed by the code that we had written for the automation. So that
          was really something that I'm really proud of.

          file for yourself, so you can work on it 24/7 and it won't disturb any
          of the other developers. And based on that workspace, based on the
          changes, your code gets tested, your code gets merged into UAT, and
          gets deployed to UAT. And then, because it gets to UAT, all the other
          developers who are working on it have to sync with it, and their
          change also goes into UAT whenever they're finished, verified, or

          main branch or the master branch, and your Terraform code stays
          stable, and 20 people can simultaneously work on the same thing in the

          20 people are now going to create 20 different state files for their
          own changes, it will create a lot of noise in the environment, and a
          lot of garbage resources in the environment. So we have to have a
          strategy in place which kind of removes this excess resource that's
          modified by each member once their changes are verified. So how do we
          do it? We create an MR, a merge request, and we run a pipeline when
          the MR gets created. That pipeline creates a workspace for you, and
          then you make changes, and once the MR is merged, the workspace gets
          closed, and your changes go to the next level. So there's another
          approach — you can create a workspace yourself, do the same things,
          and manually delete it. Or maybe there's another approach where, when
          your changes get merged, you clean up the state file and delete
          everything that your state has created. So there are approaches based
          on how much your requirement is and how much complexity you have. But
          the point being, using Terraform workspaces will solve my issue and
          let everybody work at the same time.
